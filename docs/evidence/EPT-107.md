## Plataformas

- **Android (CI):** backend real en Docker; la etapa `cuotas` siembra fixtures por SQL (service_role no tiene `INSERT` sobre facturas desde EPT-104) y lee **solo con la sesión del actor**. Maestro recorre Cuotas con PADRE y ESTUDIANTE.
- **iOS (CI):** build Release y smoke sin backend. **No** se afirma integración Auth/RLS en iOS: el simulador macOS no tiene backend. La lógica de cuotas es JavaScript común, cubierta por Jest en el job `móvil` (Linux). Una regresión exclusiva de la capa nativa iOS en esta pantalla no la detectaría CI.

## Revisión independiente

Una revisión de solo lectura (agente aparte, sin escribir) del diff completo no halló bloqueantes. Hallazgos corregidos: aserción Maestro `Pagada` exacta frente a la etiqueta accesible «Estado: Pagada» (ahora regex); `GRANT` inútil a `service_role` sobre las vistas (retirado); detalle abierto tras cambiar de alumno efectivo (ahora derivado de (alumno, factura)); validación de `alumno_id`/`factura_id` de cada ítem en el servicio. Tras las correcciones se repitieron SQL (37 OK sobre `db reset` limpio), regresión económica (491 + 703 OK), permisos (46 OK), API real, typecheck, lint y Jest (146).

## Hallazgo de CI: contexto perdido al refrescar la sesión

El E2E Android de GitHub Actions (JWT de 120 s) reveló que un refresh de token o una revalidación publicaba un nuevo estado de autenticación y la app volvía a «Hijos vinculados», perdiendo hijo, pestaña y detalle abiertos. Corrección: la sección y los datos del rol se atan a la clave `usuario:rol` (no a la identidad del objeto de estado) y el contexto de cuotas se eleva a `AccesoContenedor`; otro usuario sigue descartando todo. Cubierto por la prueba Jest «conserva hijo y pestaña cuando la sesión se revalida…».

## Migraciones, riesgos y rollback

- **Pendiente de release:** aplicar `20261015130000_ept_107_consulta_cuotas.sql` en producción. Es aditiva (dos vistas y dos funciones inmutables). **No aplicada**; solo probada localmente.
- **Rollback:** `DROP VIEW public.estado_cuotas_alumno, public.detalle_cuotas_items; DROP FUNCTION app_private.estado_cuota(NUMERIC,NUMERIC,DATE,DATE), app_private.fecha_negocio(TIMESTAMPTZ);` No toca datos.
- **Límite conocido:** el estado de un ítem depende de la lógica de pagos (EPT-101 en adelante); la vista usa las imputaciones aprobadas como única verdad del saldo y marca `inconsistente` si no coinciden.
- **Sin despliegue móvil:** no se publica en tiendas ni se documenta instalación en teléfono.
